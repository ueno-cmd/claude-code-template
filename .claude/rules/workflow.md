# 進行ルールとワークフロー

## 進行ルール

1. **着手前はプランモードで計画を提示する**
   タスクに着手する際、いきなりコードを書き始めない。必ずプランモードで作業計画を提示し、ユーザーの承認を得てから実装する。

2. **承認後は自律的に進め、計画を外れるときは相談する**
   承認後は計画の範囲内で、実装とテストを自律的に進める。
   致命的な問題が起きて計画を外れる必要が出た場合は、独断で進めない。新しいアプローチを説明し、再承認を得てから進める。

3. **ユーザーの意図を優先する**
   技術的により良い方法があっても、指示を勝手に変更したり最適化したりしない。
   改善案は、実装後に別の提案として伝える。

4. **ルールを歪めない**
   このディレクトリのルールを、都合よく解釈し直したり歪めたりしない。

5. **透明性を保つ**
   作業中は、何を実行しているか、なぜその方法を選んだかを常に明確に説明する。

6. **破壊的操作は慎重に行う**
   削除・上書きの前に、影響するファイルを明示する。可能であればドライランを行う。

## 標準ワークフロー

| # | フェーズ | やること |
|---|---------|---------|
| 1 | 要件合意 | `docs/idea/initial-requirements.md` をもとに要件を深掘りし、設計を合意する |
| 2 | ステアリング生成 | `/starter` で `docs/steering/` の4ファイルを生成し、ユーザーの確認を得る（既存プロジェクトなら `/realign` → 必要に応じて `/src-scan`） |
| 3 | 計画 | プランモードでタスクを分解し、テストと検証の手順を含む計画を立てて承認を得る |
| 4 | 実装・検証 | テストを書きながら実装し、自分でテストを実行して要件を満たしているか確かめる |
| 5 | UI調整 | 指示があった場合のみ。機能実装と動作確認が終わってから行う |
| 6 | レビュー | `/code-review` でバグを確認し、`steering-checker` エージェントでステアリングファイルとの整合を確かめる。指摘は反映する |

プロジェクトで追加のプラグイン（superpowers / frontend-design など）が有効になっている場合は、該当するフェーズでそれらを使ってよい。

## 完了報告前のセルフチェック

作業完了をユーザーに報告する前に、次の点を確認する。

- テスト・ビルドを実際に実行し、結果を確認した（実行していないものは「未実行」と明記する）
- `docs/steering/` のルールに反していない（ステアリングファイルがあるプロジェクトの場合）
- `TODO` / `FIXME` を残していないか。残す場合はその旨を報告する
- 未コミットの変更があるかどうかを報告に含める

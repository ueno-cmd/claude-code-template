# 本番環境の安全管理

本番DBの誤操作と秘密情報の漏えいを防ぐため、次の3層で守る。①が基本で、②③は AI に秘密情報を読ませないための仕組み。

| 層 | 内容 |
|---|---|
| ① 置かない | 開発環境の `.env` に本番の接続情報を書かない。どうしても必要な場合は、読み取り専用のDBユーザーを使う |
| ② 読ませない | `.claude/settings.json` の `permissions.deny` で、`.env`・`.env.*`・`.env-*`・`.env_*` の読み取りを禁止している（任意の深さ。見本の `.env.example` だけは読める） |
| ③ Bash の穴を埋める | `.claude/hooks/guard-env.js` が、`.env` に触れる Bash コマンド（`source .env` など）を実行前にブロックする |

あわせて、これらのファイルは `.gitignore` でコミットの対象から外している。

## 仕組みの限界

- AI が `.env` を読めなくても、ツールは `.env` を使える（例：`npx prisma migrate reset` は `.env` の `DATABASE_URL` に接続する）。そのため、本番の接続情報を置かない①が最も大事
- ファイル名を書かずに読む方法は止められない。たとえば `.env` があるディレクトリで実行する `grep -r` や、スクリプトの中でファイルを開く場合。OS レベルで止めたい場合は、Claude Code のサンドボックスを有効にする
- 危険なコマンド（`rm -rf`・`git push --force`）、本番DBへの破壊的な操作、APIキーを含むコミットは、このテンプレートのフックでは検査していない

## AI がブロックされたとき

- フックは引用符の中も検査する。コミットメッセージや PR 本文に `.env` と書くだけなら、`git commit -F <ファイル>` や `gh pr create --body-file <ファイル>` でファイル経由で渡す
- `.env` の中身が必要なとき、`.env` を作る・消すときは、ユーザーに依頼する

## AI が守ること

- 本番環境に対するコマンドやクエリは実行しない。必要な場合は、ユーザーが実行するコマンドとして提示する
- deny やフックにブロックされたら、別の書き方で回避しようとしない。理由をユーザーに伝えて判断を仰ぐ
- 接続情報・APIキーをコード、ログ、コミットに含めない

## プロジェクト開始時にやること

- 必要な環境変数の名前を `.env.example` に書く（値は書かない）。各自が `cp .env.example .env` でコピーして値を入れる
- フックの判定を変更したら、`node .claude/hooks/tests/guard-env.test.js` でテストを実行する
